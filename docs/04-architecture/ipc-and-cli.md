# IPC and CLI

> **TL;DR** — The Tauri webview talks to the Rust core via typed `invoke()` commands generated by `tauri-specta`. The **same binary also ships a headless CLI** (`src-tauri/src/cli/`, clap): `print`, `printers`, `profiles`, `queue` and `update`, plus `--json` for machine-readable output and `--invoke=context-menu --files-from <PATH>` for the shell extensions. Exit codes are frozen public surface and pinned by tests.

## 1. Two surfaces, one core

```
+-------------+    invoke()    +------------------+   handlers   +---------------+
| Webview UI  | -------------> | Tauri command    | -----------> | Rust modules  |
| (React)     |                | bridge           |              | (queue,       |
|             |                | (src-tauri/      |              |  engine,      |
+-------------+                |  src/ipc/)       |              |  profiles,    |
                               +------------------+              |  settings,    |
                                       ^                          |  update, …)  |
                                       |                          +---------------+
                                  +----+----------+                     ^
                                  | clap CLI      |---------------------+
                                  | (src-tauri/   |
                                  |  src/cli/)    |
                                  +---------------+
```

Both adapters are thin. The CLI is explicitly a **facade**: each subcommand calls the same path-injected core the matching Tauri command calls (`ipc::profiles::*_at`, `ipc::settings::*_at`, `platform::*`, `update::*`, `queue::persist`, `engine::*`), so there is exactly one implementation of every rule. The only logic that lives in `src/cli/` is what only a command line needs — argument vocabulary, name→id lookup, file expansion, output formatting and exit codes.

## 2. Tauri IPC commands

Commands are declared with `#[tauri::command] #[specta::specta]` and registered in one place: `tauri_specta::collect_commands!` in `src-tauri/src/lib.rs`. TypeScript bindings are generated into `src/ipc/bindings.ts` (regenerated on every debug launch and by `cargo test`'s `bindings_are_current`, so the file is never hand-edited).

> **Contract decisions worth calling out** (the shipped surface diverges from earlier drafts of this doc):
>
> - **Settings are replace-sections, not deep-merge.** `set_app_settings` overwrites each of the four wire sections wholesale with what the client sends (keeping `printers` + `schema_version`). There is no `update_settings(patch)` deep-merge command; the client sends a complete `AppSettings`.
> - **`list_profiles` ordering is built-ins-first, then customs by name** — not a flat name sort. The three built-ins always lead in canonical order (`Quick`, `Duplex BW`, `Photo Color`).
> - **`save_profile` is an upsert with id-preservation semantics**, which is what makes a client-side "undo delete" restore the same id.
> - **There is no `duplicate_profile` command.** Cloning is a client-side draft (a new profile with an empty id) that `save_profile` creates.
> - **A major-update confirmation is bound to its version.** `install_update` re-reads the manifest, so the version it would install can differ from the one the About screen asked about; for a major jump it installs only the confirmed version. See [auto-updater.md](./auto-updater.md).

### 2.2 Type definitions

`src/ipc/bindings.ts` is generated from the Rust types and is the authoritative copy. The excerpt below is kept aligned with it; when the two disagree, the generated file wins.

```ts
// --- Printers (ipc/printers.rs, platform/) ---
// There is no `PrinterInfo` type. `Printer` is the single shape every printer
// command returns, and `PrinterStatus` has four variants, not seven.
export type PrinterStatus = "ready" | "offline" | "error" | "busy";
export type PrinterKind   = "laser" | "mfp" | "wide" | "label" | "virtual";

export type Tray     = { name: string; paper: string | null; level: number | null };
export type Supplies = { cyan: number | null; magenta: number | null;
                         yellow: number | null; black: number | null };

export type Printer = {
  id: string;                    // stable spooler/queue key
  name: string;
  kind: PrinterKind;
  color: boolean;
  duplex: boolean;
  status: PrinterStatus;
  is_default: boolean;
  location: string;
  connection: string;            // "USB", "EPSON … (IPP)", …
  driver: string;
  shared: boolean;
  queued_jobs: number;
  max_dpi: number | null;
  papers: string[];
  trays: Tray[];
  supplies: Supplies;
  default_tray: string | null;
  default_paper: string | null;
};

export type DiscoveredPrinter = {
  id: string; name: string; connection: string; kind: PrinterKind; via: string;
};

export type PrinterOverride = { tray?: string | null; paper?: string | null };
export type PrinterPrefs = {
  default_printer?: string | null;
  disabled?: string[];
  routes?: Partial<{ [ext in string]: string }>;
  overrides?: Partial<{ [printerId in string]: PrinterOverride }>;
};
export type PrinterPolicy = { default_printer?: string | null };

// --- Print settings (queue/job.rs; lowercase wire enums) ---
export type Duplex      = "none" | "long" | "short";
export type ColorMode   = "color" | "monochrome";
export type PaperSize   = "a4" | "letter" | "legal" | "a3";
export type Orientation = "auto" | "portrait" | "landscape";
export type Scaling     = "fit" | "shrink" | "none";

export type JobSettings = {
  printer: string | null;        // null → app/OS default resolved at dispatch
  duplex: Duplex;
  color_mode: ColorMode;
  copies: number;                // 1..=999
  paper_size: PaperSize;
  orientation: Orientation;
  scaling: Scaling;
  page_ranges: string | null;    // "1-5,8" or null for all pages
};

export type PrintRequest = {
  files: string[];
  settings: JobSettings;
  profile_name: string | null;   // display/log only
  hold?: boolean;                // true = every job enqueued `paused` (FR-001 "add to queue");
                                 // scoped to this batch, the global pause flag is untouched
  origin?: JobOrigin | null;     // FR-124: the integration the batch came from; copied onto
                                 // every job (bounded), shown on its Queue row
};

// FR-124: `source` ≤ 32 chars, `label` ≤ 120, control characters dropped.
export type JobOrigin = { source: string; label?: string | null };

export type JobBatch = { batch_id: string; job_ids: string[] };

export type JobState =
  | "queued" | "converting" | "converted" | "printing"
  | "done" | "failed" | "paused" | "cancelled";

// `reason` / `params` are optional (absent on a queue.json written before them):
// the UI translates `code` (+ `reason`) with `params`, the same model as IpcError.
export type JobError = {
  code: string;               // stable: print_timeout, printer_unavailable, …
  message: string;            // English detail (logs, CLI, UI fallback)
  reason?: string | null;     // stable variant, e.g. "no_printer", "duplex"
  params?: Record<string, string> | null; // secs, printer, paper, detail
};
// `percent` is NULLABLE: the printing phase cannot report a fraction, so the UI
// must render an indeterminate bar rather than 0 %.
export type JobProgress = { phase: string; percent: number | null };

export type Job = {
  id: string;                    // UUID v7 (time-sortable)
  batch_id: string;
  state: JobState;
  input_path: string;
  file_name: string;
  input_ext: string;             // lowercased, no leading dot
  input_bytes: number;
  pages: number | null;
  cache_pdf: string | null;
  settings: JobSettings;
  profile_name: string | null;
  printer_resolved: string | null;
  attempts: number;
  error: JobError | null;
  progress: JobProgress | null;
  submitted_at: string;          // RFC 3339 UTC
  started_at: string | null;
  finished_at: string | null;
  origin?: JobOrigin | null;     // FR-124; absent in a queue.json written before it
};

export type QueueSnapshot = { schema_version: number; queue_paused: boolean; jobs: Job[] };

// --- File inspection + folder expansion (ipc/jobs.rs, engine/) ---
export type FileInfo = {
  path: string; name: string; ext: string; bytes: number;
  pages: number | null; supported: boolean; reason: string | null;
  reason_code: RejectReason | null; // stable form of `reason`, translated by the UI

export type ContextAction = "configure" | "print-default" | "queue";
// `truncated_from`: the real selection size when the writer had to cut it to the
// 10,000-path handoff cap; the UI warns that only the first `paths.length` arrived.
export type Selection = { paths: string[]; action: ContextAction; profile_id: string | null; truncated_from?: number | null };
```

### 2.3 Rust handler example

```rust
// src-tauri/src/ipc/jobs.rs
#[tauri::command]
#[specta::specta]
pub async fn print_files(
    state: State<'_, QueueHandle>,
    req: PrintRequest,
) -> Result<JobBatch, IpcError> {
    // `submit` validates and fans the batch out synchronously (off the IPC
    // thread), returning before any job is enqueued — a bad request never
    // reaches the queue. The dispatcher then drives the jobs and pushes
    // `queue-updated` events.
    let handle = state.inner().clone();
    run_blocking(move || handle.submit(req)).await
}
```

### 2.4 Events (push from Rust to UI)

All six events derive `tauri_specta::Event` and are collected in `src-tauri/src/lib.rs`. Event *names* are the struct identifiers kebab-cased by the derive; the webview subscribes through the generated `events` object (`events.queueUpdated.listen(…)`), never raw `listen()`.

| Event name            | TS type / payload                              | Emitted by | Notes |
| --------------------- | ---------------------------------------------- | ---------- | ----- |
| `queue-updated`       | `QueueUpdated` = `QueueSnapshot`               | Dispatcher, on every persisted mutation (submit / transition / cancel / clear / pause) | Full snapshot; the frontend replaces state wholesale |
| `job-progress-event`  | `JobProgressEvent` = `{ id, phase, percent }`  | Dispatcher's conversion progress callback | Throttled ≥ 100 ms, advisory, **not** persisted |
| `update-available`    | `UpdateAvailable` = `UpdateCheck`              | `lib.rs`'s startup thread, via `update::run_startup_check` | Emitted **only** when the preference is on, the 24 h window elapsed, the release is strictly newer, and it is not the skipped one — receiving it is already the decision to tell the user |
| `selection-forwarded` | `SelectionForwarded` = `Selection`             | The single-instance plugin callback, and the macOS Finder service | A second launch handed this window a file selection. The payload is informational: the same selection is also parked in the pending store, and the window acts on it by calling `take_pending_selections` — one destructive drain, so a selection can never be honoured twice |

| `update-download-progress` | `UpdateDownloadProgress` = `{ downloaded, total }` | `install_update`, per received chunk | Bytes so far and the `Content-Length` when known; advisory |
| `dependency-install-progress` | `DependencyInstallProgress` = `{ id, line }` | `install_dependency`, per output line of winget/brew | Shown in the consent dialog while the install runs; advisory |

There is no `printer-changed` event.

### 2.5 Capability declaration

Tauri 2's capability system gates **core and plugin** permissions (window, webview, dialog, …) per window. It does **not** gate the app's own `#[tauri::command]` handlers: commands registered through `collect_commands!` / `invoke_handler` are the application's private IPC surface and are callable from the main window regardless of the capability list. So `capabilities/main.json` carries only the core defaults plus the one plugin permission we actually use:

```json
{
  "$schema": "../gen/schemas/desktop-schema.json",
  "identifier": "main-capability",
  "description": "Permissions granted to the Pluryprint main window.",
  "windows": ["main"],
  "permissions": [
    "core:default",
    "core:window:default",
    "core:webview:default",
    "dialog:default"
  ]
}
```

`dialog:default` grants the native file-picker plugin the Print Job screen uses. (`tauri-plugin-opener` and `tauri-plugin-single-instance` are called from Rust only, so they need no JS capability.) The defense-in-depth boundary for the app's own commands is therefore twofold, and does **not** come from a per-command allowlist:

1. **Closed surface.** Only the commands enumerated in `collect_commands!` exist at all.
2. **No remote code.** The window's CSP loads only the bundled SPA and forbids remote content (see [`security-model.md`](./security-model.md) § 3.3), so there is no attacker-controlled script in the webview to call them.

## 3. CLI

> **Status: shipped.** `src-tauri/src/cli/` implements the whole surface below, `update install` included.

### 3.1 Entry point

`cli::startup(argv)` classifies the command line **before** the Tauri builder runs — a headless run never creates a webview. `cli::classify` inspects argv without parsing it, and the first **non-flag** argument decides:

1. `--invoke=context-menu` (or `--invoke context-menu`) → **context-menu mode**: the app opens with the supplied selection. This outranks everything, so a shell-extension launch can never be reinterpreted as a subcommand.
2. `--cli`, `--help`/`-h`, `--version`/`-V`, or a known subcommand (`print`, `printers`, `profiles`, `queue`, `update`, `bridge`) → **headless mode**, no window.
3. A bare argument naming an existing path → **GUI mode** ("open with" launch). Every such path (absolutized against the launch's working directory, then resolved by `canonical_input`) becomes a `configure` selection (`cli::open_with_selection`), so the app opens on the Print Job screen with the files loaded.
4. Anything else → headless, so clap can answer "unrecognized subcommand" with a non-zero code instead of silently opening a window.
5. No arguments (or only platform noise such as macOS' `-psn_0_12345`) → **GUI mode**.

**Windows: two executables.** `pluryprint.exe` is a GUI-subsystem program, so a double-click never flashes a console. Its headless path calls `cli::console::attach_parent()` first — `AttachConsole(ATTACH_PARENT_PROCESS)`, then `CONOUT$` for any standard handle that is still empty, while handles the caller redirected (`> out.txt`, a pipe) are kept — so output reaches the terminal. What it cannot change is that `cmd.exe` and PowerShell **do not wait** for a GUI-subsystem program: the prompt returns at once and `%ERRORLEVEL%` / `$LASTEXITCODE` never see the exit code.

Scripts therefore use **`pluryprint-cli.exe`**, installed next to it (`src-tauri/src/bin/pluryprint-cli.rs`): a console-subsystem build of the same CLI, run in-process, whose exit status is the §3.7 code. When its command line asks for the GUI (no subcommand, a context-menu invocation, an "open with" path) it starts `pluryprint.exe` detached with the same arguments and exits 0, so a terminal is never held open by a window. Calling `pluryprint.exe` itself from a script needs `start /wait pluryprint.exe …` (cmd) or `Start-Process -Wait -PassThru` (PowerShell) to get the code. Both executables flush stdout/stderr before exiting (`cli::exit_process`). On macOS and Linux both are plain console programs.

**Linux: the package decides the command name** (a preview platform, [ADR-0015](../adr/0015-linux-support.md)). The `.deb` puts `pluryprint` on `PATH`, so scripts call `pluryprint print …` as on macOS. An AppImage is a single file that is not on `PATH`: the command line is the AppImage itself, with the same arguments (`./Pluryprint_<version>_linux_x64.AppImage print --printer Office report.pdf`), and the exit codes are the same. The render worker that prints HTML, Markdown and text opens a hidden WebKitGTK window, so on Linux it needs a display (X11 or Wayland) even when the CLI started it.

**Second launches.** `tauri-plugin-single-instance` intercepts a second process and forwards its argv to the running instance, which re-interprets it (`cli::single_instance`) and emits `selection-forwarded` (NFR-014). Both a context-menu argv and an "open with" argv (absolute paths only — the running instance has a different working directory) resolve to a selection. The pending store is created **before** the Tauri builder and shared with the plugin callback, so a selection forwarded while the first instance is still cold-starting (before `setup`) is kept and drained with the launch's own selection, which stays first. A headless subcommand exits before that ever matters.

**Who deletes the handoff file.** The same argv is therefore interpreted *twice* — once by the process that was launched, once by the instance that actually owns the window — so reading a handoff file never deletes it (`cli::handoff::read_file`). The delete happens in whichever process ends up **parking** the selection: `PendingSelections::park_launch` when this process boots the window, or the single-instance callback when the selection was forwarded. It is always best effort, and `cli::handoff::sweep` collects anything left behind. The macOS service is the one exception: it writes and reads the file inside one process, so it can `consume` it outright. None of this weakens the validation gate — schema version, freshness window, directory containment and the size/path caps apply to every read.

### 3.3 Flag semantics

- `--files` takes a comma-separated list. Each entry may be a plain path, a **directory** (walked recursively with the same `engine::expand_folder` the GUI uses, filtered by `max_file_size_mb`), or a **wildcard in the last path component** (`C:\Reports\*.pdf`). Patterns are expanded by Pluryprint, not the shell, so they behave identically in `cmd.exe` and in bash. A pattern or folder matching nothing is an error naming the entry.
- Relative paths are resolved against the working directory **only here** and for an "open with" launch (`pluryprint-cli report.pdf` from a terminal). Every other surface refuses them (`util::paths::canonical_input`, NFR-025). An "open with" launch is resolved against the *launching* process' folder even when the app is already running: the single-instance plugin forwards the second launch's working directory, and the running instance anchors the paths there before deciding what the launch means (`cli::single_instance::interpret`).
- `--files-from <PATH>` reads a JSON handoff file instead of argv — how the shell extensions pass a large selection past Windows' 32,767-character argv cap. A handoff file is untrusted input: it must resolve **inside** the per-user handoff directory (`<data dir>/handoff`) and be fresh, or it is refused.
- `--duplex`, `--paper`, `--scale`, `--orientation`, `--quality` are case-insensitive. `--scale actual` is the engine's `none` — the one deliberate rename.
- `--paper` takes the same names as the Print Job screen and the profile editor: `a4`, `letter`, `legal`, `a3` (case-insensitive), `auto` (the printer's own default, no media sent), or any size a printer reports (`A6`, `4x6`, `Tabloid`, `w288h432`…; see `printers list`). For `print`, a size the target printer does not list is refused before anything is spooled (exit 5, `Printer`), as in the GUI. `profiles create --paper` stores the name as given, since a profile is not tied to one printer.
- `--printer` accepts the spooler **queue id** (`HP_LaserJet_Pro_M404`) or the **display name** `printers list` shows (`HP LaserJet Pro M404`, CUPS `printer-info`), the id ignoring case as CUPS does. Either way the job is spooled to the matched queue id, never to the text typed. A display name shared by several queues is refused with exit code `Printer` and the candidate ids; pass the id instead. The queue applies the same rule to a profile's printer (an unmatched or ambiguous name pauses the job as `PrinterMissing`).
- With no `--printer`, the target is the file-type route, then the org-policy default (`policy.json`), then the app default, then the OS default — the same chain the GUI queue uses.
- `--color` and `--mono` are mutually exclusive; omitting both leaves the profile's value. The same holds for `--collate` / `--no-collate`.
- `--password-file <PATH>` / `--password-stdin` (FR-059) give the password of the batch's encrypted PDFs: the first line of the file, or of standard input (`printf %s "$PW" | pluryprint print …`). There is deliberately no flag that takes the password itself, so it never shows in `ps` or the shell history; `--password-stdin` refuses a terminal, where typing would echo it. The password is read before anything prints, kept in memory only, and used to decrypt each protected PDF into the run's private cache (deleted on exit); plain files ignore it. A protected PDF without it or with a wrong one fails that file only (exit 13, `password_required` / `password_incorrect`), and one that forbids printing is refused whatever the password (`printing_not_allowed`).
- `--no-dialog` and `--wait` are accepted for compatibility and are **no-ops**: a headless `print` never opens a window and always handles each file (convert, then hand to the spooler) before exiting.
- Each file in the `print` report has a `state`: `done` means the system spooler **accepted** the job, not that paper came out (no spooler says that synchronously); `held` means it was accepted by a queue that is paused, offline or stopped on an error (out of paper, a jam, a stopped CUPS queue), so nothing prints until someone fixes the printer, or that the spooler holds the job itself even though its queue is ready (CUPS `pending-held`, e.g. a queue created with a default `job-hold-until`; a job paused or stopped in the Windows queue), read per job by its `os_job_id` (the exit code is still 0, since the job is safely queued); `unconfirmed` means it was accepted but the printer list or the job's own state could not be read, so whether it prints now is unknown (exit code unchanged, WARN `cli_printer_state_unknown` or `cli_job_state_unknown`); a file without an `os_job_id` is judged by its queue alone; `failed` carries an `error` and raises the exit code. A failed file is also logged as WARN `cli_job_failed` with the file name (never its folder), extension, printer, error code and reason; the message stays out of the log because it can quote absolute paths and SumatraPDF's log (NFR-082), and it is in the report. It is the headless counterpart of the queue's `job_failed`.
- `--json` switches every command to JSON on stdout; errors become JSON on stderr. That includes command lines the parser refuses (an unknown flag, a bad value, a missing `--files`): they come back as `{"error":{"code":"InvalidRequest","message":…}}` with exit 2. `--help` and `--version` print as text.

**What `print` does *not* do.** A headless print is a foreground operation, so it deliberately differs from the GUI queue in three ways: it never touches `queue.json` (so it cannot race a running app for it), it converts into a private temp directory deleted on exit (so neither process can delete the other's work), and it has **no retry/backoff** — a script wants an exit code, not a job that quietly retries.

**What `queue` does *not* do.** `queue status|cancel|cancel-all` operate on the persisted `queue.json` through `queue::persist`, guarded by the same `can_transition` rules the dispatcher uses. They do **not** reach into a running app: a live instance owns its queue in memory and rewrites the file on every transition, so a cancel written to the file while the app is open would be overwritten — and reported as a success while the job kept printing. The app therefore holds an exclusive OS lock on `<data_dir>/instance.lock` for its whole lifetime (`cli::instance`; released by the OS however the process ends), and `queue cancel` / `cancel-all` check it before reading and again before writing: while the app runs they **fail** with `InvalidState` (exit code 1) and change nothing, telling the user to cancel from the Queue screen. A lock that cannot be checked at all (the file cannot be opened, or the filesystem does not support locking, where the app may be running unlocked) is refused the same way: "could not tell" is never read as "the app is closed". The app retries its own claim for about half a second at startup, so a CLI probe that holds the lock for an instant cannot leave it running without one. `queue status` stays available (it only reads what the app persists). The offline path is what makes `queue status` useful in a script and `queue cancel` useful on a queue left behind by a closed app. A cancelled job that is still in the system print queue (any job with a known spooler id and printer, including one recovered as paused) is removed from it as well. On Windows the spooler reuses job ids, so the job is deleted only while it still carries the name Pluryprint spooled it under and belongs to the current user. A job that already left the spooler is not an error; one that could not be removed is listed in `spooler_errors` (`{id, os_job_id, printer, message}`) next to `cancelled` in the JSON output, and as a `warning:` line in the text output, because its paper may still come out.

Both surfaces call the same core; the table names the shared implementation rather than implying the CLI invokes the Tauri command.

| CLI command                 | Shared core                                              | Sibling IPC command |
| --------------------------- | -------------------------------------------------------- | ------------------- |
| `print`                     | `engine::convert` → `engine::print::spool` (no queue)     | `print_files` (queued) |
| `printers list`             | `platform::list_printers`                                 | `list_printers` |
| `profiles list` / `show`    | `ipc::profiles::list_profiles_at` / `get_profile_at`      | `list_profiles` / `get_profile` |
| `profiles create`           | `ipc::profiles::save_profile_at`                          | `save_profile` |
| `profiles delete`           | `ipc::profiles::delete_profile_at`                        | `delete_profile` |
| `profiles set-default`      | `ipc::profiles::set_default_profile_at`                   | `set_default_profile` |
| `queue status`              | `queue::persist` (reads `queue.json`)                     | `queue_status` (live) |
| `queue cancel` / `cancel-all` | `queue::persist` + `can_transition`                     | `cancel_job` / `cancel_all` |
| `update check`              | `update::fetch_latest` + `update::evaluate`               | `check_for_updates` |
| `update channel`            | `settings::Config` `[updater].channel`                    | `get_app_settings` / `set_app_settings` |
| `update install`            | `update::install::{find_update, install}` through a windowless Tauri app (`headless_updater_app`) | `install_update` |

#### `update install`

`update install` runs the same core as `install_update`. Without `--yes` it asks on an interactive terminal (`[y/N]`; a major update is named as such, FR-087), exits **2** when there is no terminal to ask, and exits **12** when the answer is not yes. A rejected signature or any other install failure exits **11**. `PLURYPRINT_UPDATE_ENDPOINT` replaces the manifest URL for local end-to-end tests. With `--json`, stdout is the `UpdateInstallResult` (`{"installed": "0.2.0", "restart_required": true}`, or `"installed": null` when up to date).

On Windows two more rules apply:

- **Refused while the app is open.** The per-user NSIS installer runs in passive mode and closes a running Pluryprint without asking. While the app holds its instance lock, `update install` therefore installs nothing and exits **1** (`InvalidState`), pointing at *About → Install update* in the app. macOS and Linux replace the bundle without closing the app, so they do not refuse.
- **The result is printed at hand-off.** `tauri-plugin-updater` ends the process itself (`std::process::exit`) once the verified installer has been launched, so the result (`{"installed": "0.2.0", "restart_required": false}` / `Installing Pluryprint 0.2.0`) is printed and the log is flushed from the updater's before-exit hook, after download and signature verification and just before the installer starts. Exit code 0 then means "verified and handed to the installer", not "installation finished". The installer is told not to relaunch anything: the plugin's default would replay the CLI's own `update install --yes` command line through NSIS `/ARGS`.

### 3.6 JSON output mode

With `--json`, **stdout carries nothing but the JSON document** (so `| jq` works), and errors go to stderr as `{"error":{"code":…,"message":…}}` — the same `{code, message}` envelope the webview receives, so a script and the UI never see two different names for the same failure.

Without `--json` the CLI prints a plain left-aligned text table (`cli::output::table`). Earlier drafts named `comfy-table`; it is **not** a dependency, and one table helper did not justify one.

### 3.7 Exit codes

Frozen public surface, defined by `ExitCode` in `src-tauri/src/cli/exit.rs` and pinned value-by-value by `cli_contract.rs`, so changing one fails the build rather than silently breaking a caller.

| Code | Name                  | Meaning |
| ---- | --------------------- | ------- |
| 0    | `Success`             | All requested operations succeeded. |
| 1    | `Generic`             | Generic error (catchall). Also where `JobNotFound` / `InvalidState` / `Internal` land — they have no dedicated code (except the reasons below that name one). |
| 2    | `Usage`               | Invalid command-line usage. Every clap failure except `--help`/`--version`, which exit 0. |
| 3    | `Config`              | Configuration error — unreadable/invalid `config.toml` (reason `config_corrupt`: `print` refuses to run on one rather than fall back to defaults, and the config writers such as `profiles set-default` and `update channel` refuse to overwrite one), **or a missing external dependency** (`lp`, SumatraPDF): that is an environment fault, not a usage one. |
| 4    | `Profile`             | Profile not found / invalid, including an unreadable `profiles.toml` (reasons `profiles_corrupt`, `profiles_invalid_entries`). |
| 5    | `Printer`             | Printer not found / invalid — including **a setting the driver refuses** (`UnsupportedSetting`: the flag was legal, the device is the problem) and "no printer configured at all". |
| 6    | `FileNotFound`        | One or more files not found / unreadable. |
| 7    | `UnsupportedFile`     | One or more files unsupported. |
| 8    | `ConversionFailed`    | Conversion failed (timeout or converter error). |
| 9    | `PrintFailed`         | Printing failed — the spooler reported an error, **or the print hop timed out** (it took the job and never finished). |
| 10   | `UpdateCheckFailed`   | Update check failed (network, rate limit, misconfigured repository). |
| 11   | `UpdateInstallFailed` | Update install failed: download, a rejected signature (`UpdateSignatureInvalid`), the installer, or a copy of the app that cannot update itself. |
| 12   | `Cancelled`           | User cancelled. |
| 13   | `PdfProtected`        | One or more PDFs are protected (FR-059). Reasons `password_required` / `password_incorrect`: supply the password with `--password-file <path>` or `--password-stdin` (never as an argument, so it stays out of `ps` and shell history). Reasons `printing_not_allowed` / `unsupported_encryption`: final, no password changes them. |

For batches, `ExitCode::worst` returns the highest code among the files, so one failure in fifty is never reported as success.

## 4. Error model

A single `IpcError` is serialized identically to the webview and to a `--json` CLI run (`src-tauri/src/util/error.rs`). On the wire it is one flat object:

```ts
export type IpcErrorCode =
  | "FileNotFound" | "InvalidRequest" | "UnsupportedFormat" | "ConversionFailed"
  | "PrintFailed" | "UnsupportedSetting" | "DependencyMissing" | "JobNotFound"
  | "InvalidState" | "ProfileNotFound" | "UpdateCheckFailed" | "UpdateInstallFailed"
  | "UpdateSignatureInvalid" | "Internal";

export type IpcError = {
  code: IpcErrorCode;                      // stable family, never renamed
  message: string;                         // English detail (logs, CLI, last-resort UI fallback)
  reason?: string | null;                  // stable sub-code within `code`, never renamed
  params?: { [key: string]: string } | null; // interpolation values for `reason`
};
```

In Rust the enum keeps one tuple variant per family (`IpcError::InvalidRequest(String)`, …) plus `IpcError::Localized(Box<LocalizedError>)`, which carries a family `code`, a `&'static str` `reason`, `params` and the English `message`. A `Localized` error serializes with its family `code` (never `"Localized"`), so `IpcError::code()` and `exit::exit_code_for` treat it exactly like the plain variant. A `LocalizedError` is a `std::error::Error`, so `anyhow`-based layers (the platform printer code) can return one and `From<anyhow::Error>` recovers it instead of flattening it to `Internal`.

Examples: `{"code":"FileNotFound","message":"foo.pdf"}`; `{"code":"UpdateCheckFailed","message":"github.com returned an unexpected status (502)","reason":"bad_status","params":{"status":"502"}}`.

Reasons currently emitted:

| `code` | `reason` (params) | Raised by |
| --- | --- | --- |
| `UpdateCheckFailed` | `rate_limited`, `offline`, `bad_status` (`status`), `bad_response`, `repo_missing`, `not_configured` | `update::fetch_latest`, `ipc::update` |
| `Internal` | `open_logs_failed`, `open_link_failed`, `config_corrupt`, `profiles_corrupt`, `profiles_invalid_entries` | `ipc::diag`, settings/profiles/printer prefs writes |
| `InvalidRequest` | `url_not_allowed`, `builtin_readonly`, `reserved_id`, `builtin_delete`, `delete_default`, `id_too_long`, `name_empty`, `name_too_long`, `name_taken` (`name`), `copies_out_of_range` (`copies`), `page_range`, `import_too_large`, `import_unreadable`, `import_malformed`, `import_unsupported_version` (`version`), `import_empty`, `import_invalid_profile` (`name`), `add_printer_unsupported_scheme` (`scheme`), `major_update_unconfirmed` (`version`, `current`), `major_update_changed` (`version`, `confirmed`) | `ipc::diag`, `ipc::profiles`, `platform::{cups,windows}`, `update::install` |
| `InvalidState` | `update_in_progress`, `resume_no_printer`, `resume_printer_missing` (`printer`), `resume_printer_ambiguous` (`printer`), `resume_printer_disabled` (`printer`) | `update::install`, `queue::dispatcher` (resuming a job paused because its printer is missing, shares its name with another queue, or is disabled) |

| `DependencyMissing` | `ippfind_missing` | `platform::cups` discovery |
| `PrintFailed` | `set_default_failed`, `add_printer_needs_admin` | `platform::windows` |

**Frontend mapping (FR-092).** `unwrap()` in `src/lib/ipc.ts` throws an `IpcFailure` (`src/lib/ipcError.ts`) whose `message` is already in the UI language: `common:ipcErrors.reasons.<code>.<reason>` with `params` when that key exists; otherwise the family sentence `common:ipcErrors.codes.<code>` with the English detail as `{{detail}}`; and only for an unknown `code` the raw `message`. The English detail stays on `IpcFailure.detail`. Per-file refusals use the same idea without an error: `FileInfo.reason_code` / `SkippedFile.reason` are translated by `src/lib/jobFiles.ts`. Stored job errors (`Job.error`) follow it too: `src/lib/jobError.ts` maps `queue:jobErrors.reasons.<code>.<reason>`, else `queue:jobErrors.codes.<code>`, filled with `params` (a `printer` param shows the printer's display name), and falls back to `message` for an unknown code or when a sentence needs a param the stored error lacks.

The CLI prints the `Display` form to stderr as `error: …`, or — with `--json` — the same payload wrapped as `{"error":{…}}`. `exit::exit_code_for` is the default `IpcError` → exit-code mapping (keyed on `code()`); a call site that knows better overrides it with `CliError::new`.

## 5. Stability

- IPC command names and event names are part of the **public surface** and follow semver. Renaming or removing one is a major version bump.
- CLI subcommand names, flag names and **exit-code numbers** are public surface. New flags can be added in minor versions; existing flags may be deprecated (with a warning) and removed only in a major version.
- JSON output schemas are public surface and versioned implicitly by app version. A `--cli-protocol-version` flag may be added in 2.x.

## 6. Browser bridge (Native Messaging)

> **Status: in development** (ships with 0.0.6). Decision and alternatives: [ADR-0016](../adr/0016-pluryfact-browser-bridge.md). Requirements: FR-120..FR-127.

PluryFact, the SRI invoice downloader for Chrome, Edge and Brave, sends documents to Pluryprint through **`pluryprint-bridge`**, a Chrome Native Messaging host installed next to the app (`src/bin/pluryprint-bridge.rs`, `src/bridge/`). It is a third entry point beside the GUI and the CLI, and it reaches the app through the existing context-menu path (§3.1), so nothing new is exposed by the app itself.

### 6.1 Process and framing

The browser starts the bridge with the caller's origin as `argv[1]` (Windows adds `--parent-window=<hwnd>`, which is ignored) and talks to it over stdin/stdout: each message is a 32-bit length in **native byte order** followed by that many bytes of UTF-8 JSON (`bridge::framing`). Limits are the browser's: at most **64 MiB** per message to the host (a longer frame is drained and answered `too_large`), at most **1 MB** per reply (the host never builds a larger one; `listPrinters` drops its paper lists first). stdout carries frames and nothing else; the bridge logs to the app's log file (and nowhere in tests). The process exits 0 when the browser closes stdin, 1 if the pipe breaks mid-frame.

An origin that no manifest of this host allows (`bridge::register::allowed_origins`: PluryFact's Web Store origin plus any extra origin a manifest lists) gets `origin_not_allowed` for every request.

### 6.2 Protocol v1

Every message is `{"v":1,"id":"<string ≤128 bytes>","type":"<type>",…}`. A reply repeats `v`, `id` and `type` and adds `"ok":true` with the fields below, or `"ok":false,"error":{"code","message"}` (`message` is English, for logs). Field names are camelCase. Unknown top-level fields are tolerated; unknown `overrides` fields are refused.

| `type` | Request | Reply |
| --- | --- | --- |
| `hello` | `client`, `clientVersion`, `protocols: [1]` | `host: "pluryprint"`, `hostVersion`, `protocol: 1`, `capabilities`, `limits: {maxFileBytes: 52428800, maxFiles: 5000, maxChunkBytes: 16777216, maxJobBytes: 1073741824}` |
| `listPrinters` | — | `printers: [{id, name, isDefault, capabilities?: {duplex, color, papers[]}}]` (at most 200, 64 papers each) |
| `listProfiles` | — | `profiles: [{id, name, isDefault}]` |
| `beginJob` | `source: "pluryfact"`, `label` (≤ 120 characters), `action: configure\|queue\|print-default`, `profileId?`, `printerId?`, `overrides?: {copies 1-999, duplex off\|long-edge\|short-edge, color color\|mono, paper, orientation auto\|portrait\|landscape, collate}`, `expectedFiles` (1-5000) | `jobId` (UUID v7, minted by the host) |
| `putFile` | `jobId`, `index` (`0..expectedFiles`, the print order), `name`, `kind: pdf\|xml\|txt`, `size`, `sha256` (lowercase hex of the whole document), `chunk` (`0..chunks`, in order), `chunks`, `data` (standard base64 with padding) | `received` (bytes so far), `complete` |
| `commitJob` | `jobId` | `state: "handed-off"`, `files` |
| `abortJob` | `jobId` | `state: "aborted"` |

Error codes: `unsupported_version`, `unknown_type`, `bad_request`, `origin_not_allowed`, `too_large`, `too_many_files`, `bad_pdf`, `checksum_mismatch`, `unknown_job`, `job_incomplete`, `io_error`, `launch_failed`, `internal`. An XML document that is not well formed and a text document that is not text are `bad_request`.

At most 4 jobs may be open per connection. A document restarts from chunk 0 after an error; a complete one cannot be sent twice. The canonical exchanges are the fixtures in `src-tauri/tests/fixtures/bridge-protocol/` (copied byte for byte into PluryFact), pinned by `tests/bridge_protocol_contract.rs`.

### 6.3 What the host checks and writes

- **Names** are reduced to a base name (`/` and `\` both separate), control characters and `<>:"|?*` become `_`, leading/trailing dots and spaces go, Windows device names get a `_` prefix, the extension is forced to the `kind`'s and the result is at most 120 characters (`bridge::validate::sanitize_name`).
- **Content**: size as declared, SHA-256 as announced (`checksum_mismatch`), and the kind: `%PDF-` at the start of a PDF (`bad_pdf`); XML read by the XML converter's own `decode` and `parse` (so the bridge accepts exactly what the app prints): **no DTD** (so no entity is ever declared or expanded), at most 20 MiB, 256 levels (measured before parsing) and 200 000 nodes, UTF-8 or UTF-16 with a byte-order mark, or a declared ISO-8859-1/Latin-1/Windows-1252; text read by the text converter's `decode` (UTF-8, UTF-16 with a byte-order mark, else Windows-1252), without NUL or stray control characters.
- **Inbox**: `<data dir>/inbox/<jobId>/NNNN-<name>`, written through a `.part` file and renamed when verified. Abort and an uncommitted connection close delete the job folder; the app deletes inbox entries older than 7 days at startup, removing a planted link as a link (`bridge::inbox::sweep`).
- **Handoff**: on `commitJob`, `<data dir>/handoff/pluryfact-<jobId>.json`, schema 1, `source: "pluryfact"`, the `action`, `profile_id`, the documents in order, and two optional fields any schema-1 reader may ignore: `label` and `overrides` (`printer`, `copies`, `duplex`, `color`, `paper`, `orientation`, `collate`, in the wire spelling of the profile fields). The app validates both like the rest of the file.
- **Launch**: `pluryprint --invoke=context-menu --files-from <handoff> --action <a> [--profile <id>]`, the app next to the bridge, detached (own process group on macOS/Linux; `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP`, plus `CREATE_BREAKAWAY_FROM_JOB` when the browser's job allows it, on Windows). If the app cannot be started the handoff is deleted, the reply is `launch_failed` and the job stays open.

The app shows a selection whose `source` is `pluryfact` with a **From PluryFact** badge and the label: on the Print Job screen while every file in the job came from PluryFact (a batch that joins a job the user had already started, or a job the user drops more files into, is not labelled), and on each of its rows in the Queue (`Job.origin`). With `configure` the overrides pre-fill the Print Job settings, unless the job already had files: it then keeps its profile and settings and a toast says PluryFact's were not applied. With `queue`/`print-default` they are applied on top of the profile.

### 6.4 Registration

The manifest is `com.maecly.pluryprint.json`: `name`, `description`, `path` (absolute; on Windows relative to the manifest), `type: "stdio"`, `allowed_origins`.

| OS | Manifest | Written by |
| --- | --- | --- |
| Windows | `%LOCALAPPDATA%\Pluryprint\com.maecly.pluryprint.json`, named by the default value of `HKCU\Software\Google\Chrome\…`, `…\Microsoft\Edge\…` and `…\Chromium\NativeMessagingHosts\com.maecly.pluryprint` (Brave reads Chrome's) | The NSIS post-install hook; the pre-uninstall hook removes keys and file |
| macOS | `~/Library/Application Support/{Google/Chrome, Microsoft Edge, BraveSoftware/Brave-Browser, Chromium}/NativeMessagingHosts/` | The app at every start, for each browser whose folder exists; idempotent; only from an installed `.app` bundle (never a development build) and never from an App Translocation path |
| Linux | `~/.config/{google-chrome, microsoft-edge, BraveSoftware/Brave-Browser, chromium}/NativeMessagingHosts/` (`$XDG_CONFIG_HOME`) | `pluryprint bridge install` |

`bridge install` with `--browser all` (the default) writes for the browsers found; a named browser is always written. Re-registering with `bridge install` (or **Reconnect** in Settings) keeps any extra origin a manifest already allows; `bridge uninstall` then `install` resets to PluryFact's origin only. **Windows exception:** the setup (every install and every update) rewrites the shared manifest from scratch with PluryFact's origin only, so it drops extra origins; run `pluryprint-cli bridge install --extra-origin <origin>` again after updating a development machine. Production loses nothing: PluryFact's origin is always there. `bridge status --json` prints one object per browser: `browser`, `detected`, `manifest_path`, `registered`, `points_here`, `binary_exists`, `allowed_origins`. The subcommand uses the existing exit codes (0; 1 when a manifest cannot be written or the bridge is not next to the CLI; 2 for an origin that is not `chrome-extension://<32 letters a-p>/`).

**Tests only:** `PLURYPRINT_BRIDGE_DATA_DIR=<absolute folder>` replaces the data folder (inbox, handoff, and a test manifest read for allowed origins) and turns logging off. Without it the bridge never reads a manifest from the app's data folder: the allowed origins come only from the browsers' manifests, so `bridge install --extra-origin` is the only way to add one and `bridge status`/`uninstall` see them all; `PLURYPRINT_BRIDGE_NO_LAUNCH=1` writes the handoff and answers `handed-off` without starting the app. Neither is meant for users.
