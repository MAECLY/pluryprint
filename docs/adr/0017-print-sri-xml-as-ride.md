# ADR-0017: Print SRI XML as a RIDE-like representation

## Status

Accepted

## Date

2026-11-14

## Context

Pluryfact, the browser extension that downloads a taxpayer's electronic receipts from the SRI portal (Ecuador's tax authority), saves two files per receipt: the **RIDE** PDF the portal renders and the **XML** the SRI web service authorised. The integration with Pluryprint (ADR-0016, the native-messaging host, developed in parallel) must print everything Pluryfact downloads. Some receipts arrive as **XML only**: the portal links no RIDE, or the RIDE step failed, or the user asked for XML because it is faster (the web service answers without paging the portal). Until now `.xml` was refused with `unsupported_type` (exit 7).

What an SRI XML file looks like:

- six receipt types (`factura`, `liquidacionCompra`, `notaCredito`, `notaDebito`, `guiaRemision`, `comprobanteRetencion`), each with its own schema versions (1.0.0 to 2.1.0; the retention changed shape in 2.0.0, grouping withholdings by supporting document);
- usually wrapped in the `<autorizacion>` the web service and the portal hand out, with the receipt as a **string** inside `<comprobante>` (CDATA or escaped text), or inside the whole SOAP `RespuestaAutorizacionComprobante`; sometimes a bare signed receipt;
- printed, by law and by habit, as a RIDE: issuer and document box side by side, buyer underneath, lines, then additional information and payments next to the totals, with the 49-digit access key and its Code 128 barcode.

XML is also a general format people right-click and expect to print (configuration files, exports), and printing it raw (as text) is unreadable on paper.

XML is hostile input by tradition: DTDs with recursive entities (billion laughs), external entities that read files or reach the network (XXE), and pathological nesting.

## Decision

Pluryprint prints `.xml`. A new converter, `engine::convert::xml` (route `Xml`), turns the file into an HTML page that goes through the existing web-view route ([ADR-0012](./0012-system-web-view-renderer.md)): the same staged page, policy (no scripts, no connections) and render worker as HTML, Markdown and text.

1. **SRI receipts print as a RIDE-like representation** (FR-057b). `xml::sri` recognises the three file shapes, reads the receipt inside an `<autorizacion>` as a second document under the same limits, and builds a typed model; `xml::ride` lays it out the way Ecuadorian RIDEs are laid out, in Spanish (the labels are the document's), with the Code 128 barcode generated in Rust as inline SVG (`xml::code128`). The page **never invents data**: a bare receipt says "No consta en el archivo" where the authorisation would go; a receipt the SRI did not authorise carries a banner with its state. The footer says it is a representation generated by Pluryprint from the XML, in the app's language.
2. **Any other XML prints as a readable tree** (FR-057a): one line per element with its attributes, short text inline, comments and processing instructions in grey, indentation guides per level.
3. **Untrusted input rules.** A `<!DOCTYPE` in the prolog is refused before parsing (`xml_dtd_refused`) and the parser (`roxmltree`, already in the tree through `usvg`) runs with `allow_dtd` off: no entity beyond the five predefined ones is ever expanded and nothing is ever fetched. The file is at most 20 MiB and 200,000 nodes (`xml_too_large`); nesting is measured by a flat scan before parsing, because the parser descends recursively, and refused past 256 levels (`xml_too_deep`). Everything from the file is escaped into the page. A broken inner receipt falls back to the tree view of the outer file. All four reasons are terminal.
4. **Paper.** The page follows the job's paper; with paper `auto` it is A4, the RIDE's own size.
5. The conversion runs in-process, like Markdown and text: parsing is bounded by the limits above and produces data, not code; the rendering happens in the capped render worker. The converter's own code has no panicking path on any input (slices are taken only on verified ASCII, arithmetic is checked), which a mutation test over the fixtures exercises.

## Alternatives Considered

| Option | Why not |
|---|---|
| Keep refusing XML; make Pluryfact always download the RIDE PDF | The portal does not always offer one, it is the slow path, and XML-only receipts would stay unprintable. |
| Print the XML as plain text (the `txt` route) | Unreadable on paper, and an accountant cannot use it as a receipt. |
| XSLT stylesheet in the web view | WebKit and WebView2 would run XSLT against a file we do not control; it reopens DTD/entity handling inside the browser and needs scripts or remote resources for barcodes. |
| Generate the PDF directly (`printpdf`/`lopdf`) | A second layout engine to maintain, with its own fonts, line breaking and pagination, when the web-view route already paginates on the job's paper. |
| A barcode crate | A dependency for 100 lines of table-driven code, which the tests check against an independent implementation. |
| `quick-xml` | Also in the tree, but a streaming reader would mean writing the tree ourselves; `roxmltree` gives a read-only DOM with the DTD switch and a node limit. |

## Consequences

### Positive

- Everything Pluryfact downloads prints, including XML-only receipts, and an SRI XML double-clicked, right-clicked or passed to `pluryprint print` prints too, without Pluryfact.
- One rendering path: pagination, paper, policy and memory cap are the web view's, already hardened.
- Any XML file prints legibly instead of being refused.

### Negative

- Pluryprint now owns a reading of six SRI schemas. A new version or a new field needs a change here; an unknown version is read with the newest version's field names, and a missing field is left out rather than guessed.
- The page is a representation generated by Pluryprint, not the issuer's RIDE: it says so in its footer, and it has no logo (the XML carries none).
- `.xml` covers many files that are not documents (Office internals, SVG-like dialects saved as `.xml`, configuration). They print as a tree, which is legible but may be long.

### Risks / Open Questions

- **Legal standing.** The SRI allows any representation that carries the receipt's data; this one is not certified. The footer and the absence of invented data are the mitigation; the receipt's authenticity is checked with the access key on the SRI's site, as with any RIDE.
- **Parsing in-process.** Release builds abort on panic, so a panic inside `roxmltree` (which reports errors as values) would end the app or the CLI, exactly as a panic in `pulldown-cmark` would for Markdown. If a review finds one, the XML step moves into the render worker, which already isolates the web view.
- **Totals are the file's.** Pluryprint prints the amounts as written, never rounded or recomputed (except the retention total, which the XML does not carry: it is the exact sum of the amounts withheld, with every decimal they have, never rounded, and the page labels it "Total retenido (calculado)"). ICE and tip rows appear only when the file carries them, never as an invented 0.00.
